Design refinement beyond the original

Align input definitions before arranging controls
One question per control

  1. 01

    Each selection should answer one clear question

    “Fuel price lookup / Consumption calculation” are tool tasks; “Calculate consumption / Calculate cost” are calculation goals. Focusing this page on consumption avoids stacking unrelated modes and fuel-price inputs above the main task.

  2. 02

    Distinguish fuel added from fuel consumed

    The original field said “fuel consumed” while its placeholder said “fuel added”. Standardise it as “fuel consumed in this interval” and require the same interval as the distance. With two full-tank records, use the distance between fills and the amount added at the second fill.

  3. 03

    Show the unit and basis beside the result

    Make “7.50 L / 100 km” the primary result, followed by “31.5 ÷ 420 × 100”. Keep inputs editable. Without vehicle and road context, avoid unsupported high/low judgements.

Task loop

Let every step answer the user's current question

  1. 01 / CHOOSE THE GOAL

    What am I calculating?

    First confirm “Calculate consumption” so the current mode matches the inputs below.

  2. 02 / ENTER RECORDS

    What data should I provide?

    Clarify that distance and fuel cover the same interval. Keep field names and units visible beyond placeholders.

  3. 03 / READ THE RESULT

    What does this number mean?

    Show “L / 100 km”, the original inputs and the formula to support checking.

  4. 04 / ADJUST AGAIN

    Can I correct a mistake?

    Retain valid inputs, guide corrections inline and clearly request recalculation after changes.

DESIGN REFINEMENT / INTERACTIVE EXAMPLE

Use a checkable example
to clarify input and feedback

Distance between two full-tank fills 420 km Fuel added at the second full fill 31.5 L Estimated consumption for this interval 7.50 L / 100 km 。

Demonstrates input, validation, calculation feedback and recalculation. Runs entirely on this page; no live fuel-price data is requested.

Define the measurement interval first

Use records from two actual full-tank fills, or accurately measured fuel consumption. Do not substitute the cumulative odometer reading or an arbitrary single fill.

State coverage checklist

Explain recovery as clearly as the main flow

01 / EMPTY INPUT

Give actionable guidance

If either input is missing, ask for distance or fuel consumed. Preserve the other valid entry instead of pushing the problem to the next step.

02 / INVALID VALUE

Explain why, preserve valid data

Show inline feedback for zero, negative or invalid values. Retain the other field so only the incorrect one needs fixing.

03 / CALCULATED

Make the result explainable and checkable

Show two decimal places, units, the formula and the matching inputs. Explain through evidence rather than an unsupported quality label.

04 / INPUT CHANGED

Invalidate the previous result promptly

After an edit, show “Recalculate” so the previous result is not mistaken for one based on the current inputs.

Reusable design methods and their application
Decision to make Explicit input for collaborators How to apply it to a new tool
01 Define the task “In what context, with which inputs, can the user obtain a useful result?” Moon phases use a date; consumption uses distance and fuel from the same interval. Define the inputs before the page structure.
02 Constrain generation Specify hierarchy, primary actions, units and data sources. List initial, processing, failure and completed states. Ask AI to generate under checkable constraints, then inspect each one to reduce purely visual trial and error.
03 Review the experience Provide a normal example, invalid inputs and an edit-and-retry path. Check correctness, error recovery, result explanations and consistency between states.
Next-round validation plan

Test the value of tools and methods with three concrete questions

The following tests are proposed, not completed. They will help decide what to change and whether to keep investing.

01 / CONTEXT FIT

Does reading news naturally create a need for a tool?

Test “fuel-price update → local fuel-price lookup” as a candidate context to assess whether content naturally connects to the task.

How to test
Add a clear entry after relevant content; observe entry, lookup completion and the return to reading.
Evidence to collect
Record task completion and drop-off as well as entry clicks. If users leave immediately, check the entry's promise against the tool's capability.
02 / INDEPENDENT USABILITY

Can a first-time user calculate without an explanation?

Provide distance and fuel records for the same interval; ask first-time users to calculate consumption and explain the result independently.

How to test
Observe input comprehension, units, error recovery and recalculation; record requests for help and backtracking.
Evidence to collect
Can users finish and explain “L / 100 km”? If they repeatedly confuse fuel added with fuel consumed, revise the input definition first.
03 / METHOD REUSE

Can another collaborator build a complete tool from the notes?

Choose a new lightweight tool task. Ask a collaborator to produce a first version using the notes, then review it with the same checklist.

How to test
Keep clarification, AI generation, manual correction and review records; mark rules that still need explanation.
Evidence to collect
Compare clarification rounds, omitted states and correction types. Write recurring issues back into the document before judging reuse benefits.
